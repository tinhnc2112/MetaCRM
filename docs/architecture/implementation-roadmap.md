# Implementation roadmap

Baseline: [current architecture](current-architecture.md). This is a dependency-aware plan, not authorization to deploy, alter production data or silently break contracts. Each milestone is a small PR with tests, diff review and documentation updates. `KEEP` boundaries are preserved; `REFACTOR` is incremental; `REMOVE` requires consumer check; `REDESIGN` permissions awaits product input. No new infrastructure is a prerequisite. Tests against disposable MySQL are explicitly distinct from current SQLite tests.

| Milestone | Objective and scope | Dependencies; affected components | Acceptance and required verification | Migration/compatibility; rollback |
|---|---|---|---|---|
| M0 — reproducible baseline | Pin supported runtime, establish documented lint and test commands; do not change business logic. | None; `pyproject.toml`, requirements, CI, desktop/extension manifests. | Python >=3.13 + disposable MySQL, unit suite and migration heads recorded; desktop and extension builds; lint findings triaged against baseline, not silently fixed wholesale. | Preserve current clients; revert CI/config if it rejects working paths unexpectedly. |
| M1 — secure diagnostics | Gate/remove public debug selftest; remove token prefix and raw customer content from logs; bound webhook body. | M0; `api/facebook.py`, `api/webhook.py`, middleware, tests. | Anonymous request cannot exercise debug ingestion; no credentials/PII in captured logs; valid signed webhook still works; security negative tests. | Determine if diagnostic endpoints have consumers; deprecate first if needed. Revert app changes while keeping log redaction if operational impact. |
| M2 — production secret validation | Reject default signing secret in production, document key setup/rotation; maintain dev/test convenience. | M0; config, JWT, startup, runbook. | Startup negative/positive config tests; tokens from the wrong key fail; no key logged. | Rotation needs old-token expiry and encrypted Facebook-token migration plan; rollback only with compatible keys. |
| M3 — webhook collision safety | Catch duplicate-mid insertion races; preserve existing HMAC and one notification per newly committed message. | M0–M1; Messenger service, webhook API, DB tests. | Parallel deliveries against MySQL produce one row per mid, no false permanent error; unknown Page remains ignored; invalid HMAC rejected. | No schema needed; revert code if regression; keep unique constraint. |
| M4 — order/inventory MySQL invariants | Exercise parallel order confirm/cancel/adjust and deadlock paths; fix confirmed defects only. | M0; Orders, Inventory, migrations/tests. | Balance never negative; one movement per item/transition; event and balance rollback together; deterministic MySQL integration run. | Preserve endpoint and idempotency response; additive migration only if proven needed; rollback code with schema compatibility. |
| M5 — outbound message recovery | Define unknown Graph outcome, reconciliation and safe send retry behavior. | M0, M3; conversation send, message model, desktop retry UX. | Provider-success/DB-failure and timeout tests show no blind duplicate resend; operators can reconcile and see uncertain status. | Additive state if required; old client contract remains valid; roll back consumer change but reconcile outstanding sends manually. |
| M6 — action authorization | Agree employee/admin permission matrix, then enforce Page + operation checks on mutations and sensitive reads. | **Product decision gate**, M0; auth/roles, all APIs, desktop navigation. | Matrix tests per action, role and Page; unauthorized mutations return 403; admin journey preserved. | This changes privileges: stage role grants and client behavior, preserve existing account access during transition; rollback permissions policy with audit. |
| M7 — contract and docs | Document actual `/api/v1` routes, idempotency/errors and health endpoints; resolve duplicate version/unused prefix and stale README. | M0–M6 where contracts changed; router, schemas, docs, desktop/extension. | OpenAPI/consumer contract checks pass; no undocumented route move; quick-start commands match runtime. | Deprecate legacy route only with usage evidence; restore alias if consumers break. |
| M8 — extension/realtime honesty | Align extension connection state with authenticated Page-scoped WS, or explicitly use health-only status; test reconnect refetch. | M0, M7; extension WS/connection service, desktop inbox, API WS. | Extension never reports connected for rejected WS; Page A cannot receive Page B; reload gets authoritative state. | Preserve existing HTTP status UI; feature-switch or revert WS behavior without DB migration. Multi-worker fan-out is a later evidence-driven decision. |
| M9 — legacy cleanup | Inventory consumers of root AI Sale BOT and WIP snapshots, correct entry docs, remove only confirmed unused artifacts. | M7; root `main.py`, `backend/{config,database,models,services}`, backup/diff files, README. | `rg` imports, packaging/start commands and full suite/builds prove active app unchanged; review tracked file list. | Keep legacy entry until usage disproved; git revert restores sources/docs; no data migration. |
| M10 — continued product delivery | Choose one validated next user journey (e.g. reliable Messenger-assisted order capture or manual shipment); implement smallest vertical slice. | M3–M8 as relevant; backend domain/API, desktop, extension only if necessary. | Product acceptance criteria approved for new behavior, contract/integration/E2E tests, operational error handling and observability. | Preserve current API/schema with additive evolution; reversible rollout, explicit data repair path. Scope of AI automation, POS/payment and J&T remains an open product decision. |

Release order is M0 → M1/M2 → M3/M4 → M5; M6 waits for product permission semantics; M7 then M8/M9; M10 draws only on the milestones its selected journey requires. Parallel work is possible after M0 where scopes do not overlap. Validate each migration with backup, forward run, invariant check and rollback/roll-forward rehearsal before live use. A real carrier provider requires its own later milestone after confirmed API access, credentials and an unknown-outcome recovery design. Operational SLO, scale, PII retention and recovery targets remain open; do not invent them from current code.
